# Native query field contract

`direct_mapping.SOURCE_CONTRACTS` is the existing server-owned operation contract. An operation may declare `native_field_bindings` as a set of exact `(source_path, source_type, target_doctype, target_field, fieldtype, transformation)` tuples. The current business-approved generic native Field set is empty. `Customer.alias` was a technical fixture in step 30; it is not an approved mapping for a person's or company's name. Closed purpose-specific native adapters and their existing reviewed projections are unchanged.

The rule validator checks the current server contract, Query operation and exact source type, purpose and transformation, existing DocType write permission, protected/reserved fields, and actual writable, visible, non-fetched, non-virtual field metadata. Native links require their existing reviewed resolver rather than a raw foreign id. The server checks the current native binding again when an active runtime plan is read, so removing a binding prevents a stale saved rule from executing. A native Field rule requires the explicit selected read-mapping path; the unbound legacy global-plan path cannot execute it. Snapshot fingerprint, parent/field identity, personal-draft revision and CAS are enforced by existing storage/controller boundaries; execution still needs a saved Read Service approval for the exact active mapping revision. A change to the code-owned binding is a deployable contract change and does not auto-approve any mapping or service.

A client, personal Draft, configuration import, or schema package cannot add server bindings. Shared mapping imports are restricted to the exact v1/v2 envelope keys and exact definition keys; unknown package keys are rejected. Personal imports retain their existing exact direction, identity, snapshot, revision and write-permission checks. Schema preview/adoption and its DDL/DML separation are unchanged.

Synthetic tests may inject multiple bindings into the existing in-memory contract in an isolated process; those entries are not release data or business approval. Additional business bindings require semantic evidence and an explicit review, then a data-only edit of this existing contract and targeted tests. Project naming, protected notes and mutation writeback are independent contracts and are not relaxed by this mechanism.
